Trilha Git e GitHub

Guia Definitivo: Git e GitHub para Desenvolvedores

Do zero ao avançado: versionamento local, colaboração em equipe, engenharia de histórico e automação.

Git vs. GitHub: Git é o programa instalado no computador que registra versões do projeto. GitHub é a plataforma na nuvem onde essas versões podem ser armazenadas e compartilhadas.

1. Nível básico: o fluxo local e o primeiro repositório

O nível iniciante ensina a versionar projetos pessoais sem enviar arquivos desnecessários, criar repositórios e usar o terminal com segurança.

As 3 áreas do Git local

  1. Working Directory: a pasta do projeto, onde os arquivos são criados e alterados.
  2. Staging Area (Index): a área de preparação, onde você seleciona o que entrará no próximo commit.
  3. Local Repository: o histórico local, onde as versões são salvas com git commit.
[ Working Directory ] ── git add ──► [ Staging Area ] ── git commit ──► [ Local Repository ]

Comandos essenciais

git init                         # inicializa o repositório
git status                      # mostra o estado dos arquivos
git add .                       # prepara as alterações
git commit -m "feat: primeira versão"
git log                         # exibe o histórico
git remote add origin URL       # conecta ao GitHub
git push -u origin main         # envia a branch principal

A regra de ouro do .gitignore

Em projetos Node.js e TypeScript, não envie node_modules/, dist/ nem .env. Dependências podem ser recriadas com npm install, arquivos compilados são gerados pelo build e segredos nunca devem entrar no histórico.

node_modules/
dist/
.env
Atenção: se uma pasta já foi rastreada, adicioná-la ao .gitignore não basta. Remova-a do índice com git rm -r --cached nome-da-pasta.

2. Nível intermediário: colaboração, branches e Pull Requests

Em equipes, cada funcionalidade deve ser desenvolvida em uma branch isolada. Assim, ninguém precisa commitar diretamente na main.

Branches (ramificações)

git branch nome-da-branch
git switch -c feature/login       # cria e troca para a branch
git push -u origin feature/login  # publica a branch
git switch main
git merge feature/login           # integra a funcionalidade

Branches permitem testar e revisar uma mudança antes de integrá-la ao código principal.

Conflitos de merge

Um conflito acontece quando branches alteram a mesma linha. O Git pausa a operação e marca o arquivo com <<<<<<< HEAD, ======= e >>>>>>>. Edite o arquivo escolhendo a versão correta, remova os marcadores e finalize:

git add arquivo-resolvido.js
git commit -m "fix: resolve conflito de integração"

Pull Requests e revisão no GitHub

  1. Envie sua branch com git push origin feature/login.
  2. Abra um Pull Request no GitHub para a main.
  3. Receba comentários, faça ajustes e aguarde a aprovação.
  4. Faça o merge somente depois da revisão e das verificações automáticas.

Commits semânticos

  • feat: nova funcionalidade.
  • fix: correção de bug.
  • refactor: melhoria estrutural sem mudar o comportamento.
  • docs: alteração exclusivamente documental.

3. Nível avançado: histórico e automação

O nível avançado ensina a limpar históricos, transportar commits específicos, recuperar alterações e automatizar a qualidade do projeto.

merge versus rebase

merge preserva os históricos paralelos e cria um commit de integração. rebase reaplica seus commits sobre a branch mais atualizada, produzindo um histórico linear. Não faça rebase de commits públicos que outras pessoas já usam.

git switch feature/login
git fetch origin
git rebase origin/main
git rebase -i HEAD~3              # reorganiza os 3 últimos commits

Ferramentas de emergência

  • git stash guarda alterações temporariamente; git stash pop recupera-as.
  • git cherry-pick HASH copia um commit específico para a branch atual.
  • git reflog registra movimentos do HEAD e ajuda a recuperar commits ou branches.

Hooks e GitHub Actions

Hooks, com ferramentas como Husky, executam verificações locais antes de um commit, como ESLint, Prettier e tsc --noEmit. GitHub Actions executa CI/CD na nuvem, por exemplo rodando testes unitários e validando a compilação em cada Pull Request.

# Exemplo de verificação local
npm run lint
npm test
npx tsc --noEmit
Objetivo profissional: um histórico rastreável, branches pequenas, Pull Requests revisados e uma pipeline que impeça código quebrado de chegar à produção.
